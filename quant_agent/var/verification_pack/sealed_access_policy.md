# 封存区间访问政策与入口审计（评审第 3 轮）

新封存区间：2026-09-01 起（constitution_005）。本文件回答两个问题：
谁可能读到封存数据；已发生的读取是否影响了研究选择。

## 一、全部计算入口审计

| 入口 | 路径 | 封存数据可达性 | 处置 |
|---|---|---|---|
| 研究循环回测 | orchestrator/loop.py → runner.run → run_window | 代码级拒跑：窗口触及封存界即抛错（`_allow_sealed` 未设） | 已生效，S9 测试 |
| 滚动验证/压力/bootstrap | validation/evaluate.py → run_window | 同上（全部经 run_window 唯一执行入口） | 已生效 |
| 独立封存评估 | validation/sealed_eval.py | 显式设置 `_allow_sealed=True`，全系统唯一放行点 | 允许，结果只写 sealed_evaluations，不回传循环 |
| 前向模拟 | forward/daily_forward.py | 逐日重放天然读取最近行情（含封存内的"今天"） | 允许（前向观察的定义使然）；每次运行写 sealed_access_log.jsonl |
| 批次脚本 batch*.py | 直接 runner.run | 仅 IS/DEV 窗口 | 无封存触及 |
| Context 特征预计算 | backtest/runner.py Context | 对全日历计算特征（含封存日） | 计算≠消费；所有消费点在上表已守卫 |

`_allow_sealed` 是普通 dict 键而非权限系统——真正的隔离在于：研究循环内的
constitution 一律来自 load_constitution()（quant_agent.CONFIG），该文件不含
放行键；任何想越界的调用必须显式改代码，这属于审查可见的变更（git 可查）。

## 二、九月数据使用核查（是否影响研究选择）

已发生的封存区读取仅一类：daily_forward 每日前向运行（引擎重放至最近 K 线）。
对这些产物的查看记录：

1. 批次三期间查看过回填成交列表与若干日"0 只放行"现象，用途为链路调试
   （确认 filt 在真实数据上正常工作）；
2. 未基于任何前向观察修改策略参数、评分函数、Gate 门槛或候选股票池——
   期间全部变更来自评审意见与 IS/DEV 窗口实验，可在 git 历史与
   corrections 表中逐一对应；
3. Gate 门槛数值自 constitution_003 起未变（v4/v5 仅改窗口语义与费用模型）。

**结论**：截至 2026-09-30，2026-09 区间的封存身份有条件成立。保留条件：
每次 daily_forward 运行持续记录访问日志；若未来发现任何策略/门槛/候选
变更可追溯至前向观察，该区间即刻整体降级，前向证据从头积累。

## 三、结论分层（评审第 3 轮要求的诚实表述）

| 层面 | 结论 | 支持 |
|---|---|---|
| 正常调用路径拒绝封存窗口 | 成立 | S9 测试 + run_window 代码级拒跑 |
| 研究进程无法绕过读取 | **不成立**（未证明，且理论上不可证明） | 研究进程持有代码与数据文件写权限，直接调 qengine.run_r443 或读缓存文件即可绕过 run_window——程序约定挡不住同进程代码。能提供的是追溯（git/日志），不是阻止 |

因此：九月区间**暂列为有条件保留的评估区间**；更可靠的后续证据来自策略与门槛锁定之后的新时间段。访问日志持续记录，一旦发现可追溯的选择使用即刻降级。
